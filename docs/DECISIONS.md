# Decisions

Dated entries for anything that deviates from or refines docs/PLAN.md.

## 31 Oct 2026 — Build location (temporary)

`aidigitallabs/tumble-trail` did not exist when the build started, so the game is being
built under `cc-ops/games/tumble-trail` on branch `ccr-c90fa07a-a1hn6q`. It is written as a
standalone project (own package.json, own `.github/workflows/`) so it can be moved with
`git subtree split --prefix=games/tumble-trail` once the repo exists. Until then the
workflows in `.github/workflows/` do not run (they are not at the cc-ops root) and the Pages
URL does not exist. Agents run the same checks locally instead.

## 31 Oct 2026 — Playwright

The build environment has Playwright 1.63.0 and Chromium 1243 preinstalled under
`/opt/pw-browsers`. `@playwright/test` is pinned to 1.63.0 and `npx playwright install` is
NOT run locally (CI runs it). `executablePath` is taken from `PLAYWRIGHT_CHROMIUM_PATH` when
set, otherwise the bundled browser is used.

## 31 Oct 2026 — Phase 0 decisions

- **Extra dev dependencies.** `@types/three` (three ships no type declarations; strict TS needs
  them), `@eslint/js` and `globals` (the standard building blocks of the eslint flat config that
  typescript-eslint documents). None are runtime dependencies. No other additions beyond PLAN
  section 3. `workbox-build` and `workbox-window` come in as peers of `vite-plugin-pwa` and are not
  listed separately.
- **TypeScript 6.0.3, not 7.x.** `npm view typescript` reports 7.0.2, but the latest
  `typescript-eslint` (8.72.1) declares `typescript: >=4.8.4 <6.1.0`, so npm resolved 6.0.3. Not
  downgraded by hand; bump both once typescript-eslint supports 7.
- **Prettier.** `.prettierrc.json` sets `singleQuote` and `printWidth: 100` (otherwise defaults).
  Small deviation from "defaults" to keep lines readable. `docs/PLAN.md` is excluded from prettier
  so the spec text is never reformatted.
- **Lint script** is `eslint . && prettier --check .`, so one `npm run lint` covers both.
- **`npm run build`** is `tsc --noEmit && vite build`, so a type error fails the build too.
- **Service worker.** `vite-plugin-pwa` with `registerType: 'prompt'`, `injectRegister: false`
  and a manual `registerSW()` call in `main.ts`, skipped in dev. `workbox.maximumFileSizeToCacheInBytes`
  is raised to 8 MiB because the Rapier-compat bundle (WASM embedded as base64) is about 4.8 MB
  raw; without this the main chunk would silently not be precached. `chunkSizeWarningLimit` is
  raised to match so the build log is not noisy. Applying updates only on the title screen arrives
  in Phase 4; Phase 0 just registers.
- **CI wiring.** `ci.yml` runs on pushes to every branch except `main`, on pull requests, and as a
  reusable workflow. `pages.yml` (push to `main`) calls it first and only deploys if it passes, so
  `main` pushes run CI exactly once.
- **e2e server.** Playwright's `webServer` runs `npm run build && vite preview` with
  `VITE_BASE=/`, so e2e always tests a fresh production build, locally and in CI.
- **`__tt` in Phase 0.** Only `state`, `stats()`, `ball()` (position and velocity, `t` and
  `lateral` are 0) and `app.rendererString` exist. The smoke test uses `ball()` to prove Rapier is
  stepping (the ball drops from 4 m and rests on the plane) and `rendererString` to prove WebGL is
  real. The rest of the contract arrives in Phase 1b.
- **Icons.** Generated by `scripts/make-icons.mjs` with `sharp` from an inline SVG (red and white
  quartered ball, dark rim, pastel sky and meadow). PNGs are committed in `public/icons/`:
  192, 512, 512 maskable and a 180 px full-bleed apple-touch-icon.

## 31 Oct 2026 — Phase 1a decisions

- **`buildRibbonGeometry` takes a fifth, optional `options` argument** (`{ finishM?, colors? }`).
  PLAN gives a four-argument signature, but the function needs `finishM` (to drop the walls for the
  last 2 m and to build the end pad and back wall) and the track/stripe/wall colours (vertex colours).
  Without `finishM` there is no end pad. Colours default to the meadow palette. Four-argument calls
  still work.
- **Walls are thin prisms, not single sheets.** "Outward-facing" single-sided walls would be culled
  (invisible) from the chase camera inside the track. Each wall is a closed-on-top prism of thickness
  `track.wallThicknessM` (0.3 m) built _outside_ the playable width (inner face at exactly +/- width/2),
  with inner face, outer face, top and end caps; every triangle faces out of the solid. Walls are
  vertical (world Y), not along the frame `up`.
- **Floor is non-indexed with flat normals**: three strips (left, centre stripe, right) per frame
  segment. The centre stripe is dashed (1.5 m on, 1.5 m off, `track.*`) so speed reads; hard colour
  edges need unshared vertices.
- **End pad**: always at least 6 m, rounded up to the 0.5 m frame grid (so 6.0-6.5 m), straight and
  flat (the final tangent flattened to XZ; a sloped finish would kink, none of the planned levels
  finishes on a slope). Pad side walls use the mode's height, or `low` when the mode is `none`; the
  back wall uses the same height. The start-pad disc is Phase 2.
- **`noWallSpansM` is applied whatever the wall mode.** The pure function does what it is told;
  the caller passes `[]` for Tiny (the spans are a Big kid concept).
- **`Progress.t` is the high-water mark in arc metres** (checkpoints and `finishM` are metres, PLAN
  section 6). `arcM` is the current projection (sub-frame, can go down), `t = max(t, arcM)`.
  `reseed(index)` re-centres the search window and keeps `t`: the high-water mark never decreases,
  not even across a respawn. `update()` returns `{ checkpoints, finished }` events for that step.
  Nearest frame is by 3D distance inside the window.
- **`validateLevel` stub** returns `{ ok, errors: [{ rule, message }] }`; for coincident / too-close
  points it reports the spacing errors and skips the arc-length check (a curve through coincident
  points is degenerate).
- **`levelTest` geometry**: the S-bend is two opposite 3 m lane shifts of 14 m each
  (`x = D (u - sin 2 pi u / 2 pi)`), so the heading is exactly straight where they meet and the
  turning radius stays >= 8 m. Ramps ease in and out (slope factors 0.4, 0.8, 1, 1, 0.8, 0.4 of
  15 deg); a hard corner made the Catmull-Rom overshoot to 18 deg. Measured: arc length 99.6 m,
  max slope 15.5 deg, min turning radius 8.35 m, plateau at 2.96 m. Checkpoints 25 / 50 / 72 m;
  bumps at 12 and 34 m; balloons at 19 / 41 / 62 / 84 m (gaps <= 25 m).
- **Brand colours.** The 3:1 contrast requirement against light pastel track/stripe/sky forces the
  ball main colours to be saturated mid-dark (red 0xc62828, blue 0x1d5fbf, teal-green 0x1b7f4b);
  the pastels live on the track, sky and decor. The green is blue-leaning so it separates from the
  red for colour-blind players. Ball ids: `ruby`, `indigo`, `clover`.
- **`tuning.ts` imports `Tier` as a type from `levels/schema.ts`**, and `schema.ts` imports
  `tuning` (a value): a type-only cycle, no runtime cycle. Gameplay constants from PLAN section 6
  that are not in the per-tier table (ball body, input, respawn, stuck detection) are in `tuning`
  already so Phase 1b adds no magic numbers.

## 31 Oct 2026 — Phase 1b decisions

- **`GameWorld.ts` added (not in the PLAN section 4 file list).** The determinism test and
  `fastForward` need the whole simulation (Rapier world, colliders, ball, `Progress`, checkpoints,
  finish, respawn, autopilot) without a renderer, DOM or clock. `GameWorld` owns exactly that and
  `App` owns the renderer, scene, input, camera and state machine. `Ball.ts` still holds the body,
  mesh, shadow and `applyControls` as specified; `Autopilot.ts` is a pure function called from
  `GameWorld.step`. No new dependency.
- **`buildColliders(world, geoms)` keeps the two-argument signature**; the catch plane's height comes
  from the floor geometry's bounding box (every floor strip is horizontal across the track, so its
  lowest vertex is the lowest frame). It is a large fixed cuboid whose top face is 10 m below that;
  a ball within `tuning.physics.catchPlaneHitM` (1 m) of it counts as a catch-plane fall. In practice
  the `fallDepth` (6 m) check fires first; the plane is the last resort.
- **`TriMeshFlags.FIX_INTERNAL_EDGES` is value 144 in this Rapier version**, i.e. it already includes
  MERGE_DUPLICATE_VERTICES (our geometry is non-indexed, so indices are 0..n-1 and Rapier merges the
  shared vertices). Used as-is.
- **Control forces are applied as impulses `F * dt` each step** (`applyImpulse`), not `addForce`, so
  nothing persists between steps and no `resetForces` bookkeeping is needed. Linear damping is set
  every step (0.2 driving, `brakeDamping` otherwise). Bodies are created with `setCanSleep(false)` so
  the stuck timer and control forces never meet a sleeping body.
- **Start spawn**: the first start places the ball at arc `tuning.physics.startArcM = 1 m` (frame 2)
  `+ up x 1 m`, not on frame 0, because the 3 m start-pad disc is a Phase 2 task and the floor's
  edge would otherwise sit under the ball's centre. Checkpoint respawns use the checkpoint frame
  exactly as PLAN section 6 says.
- **Respawn is counted in physics steps** (300 ms = 18 steps at 60 Hz), never from a clock. Detecting
  the fall starts the sequence on the same step: scale-out over the first half, teleport at the
  midpoint (position, zero velocities, identity rotation, `Progress.reseed`), scale-in over the
  second half. Physics is not stepped and input is ignored throughout. `GameWorld.respawnCount`
  increments at the teleport and `App` hard-snaps the camera when it changes. No vignette in 1b
  (Phase 5).
- **`Input` is split into a DOM-free core and `attach()`**, so its rules are unit tested. Time-based
  behaviour (still-finger decay, 500 ms lockout, keyboard ramp) advances in `Input.update(dt)`, called
  once per rendered frame with the real frame time; the physics step only reads `Input.controls`, so
  the step never reads a clock. Steer is exactly PLAN section 6 (plain `clamp(dx / range)` outside a
  40 px dead zone, so it steps from 0 to about 0.24 at the dead-zone edge; not rescaled).
  Keyboard (dev only): arrows / A D steer, Up / W / Space drive in hold mode.
- **Lockout on every state change**: `App.setState` calls `Input.lock()` (releases the pointer, 500 ms
  lockout), so a finger already down at load or finish never counts; a fresh pointerdown is needed.
- **Camera smooths the heading as specified and also the `trackRise` term** with the same rate, so
  the camera does not step vertically when the frame `cameraBack` metres behind changes on a ramp
  crest. Position is otherwise rigid to the (interpolated) ball.
- **Autopilot look-ahead term** = `lookAheadGain (0.5) * (sideways offset of the frame 4 m ahead,
measured in the current frame's right) / (width / 4)`; both constants are in `tuning.autopilot`.
  Obstacle repulsion arrives with obstacles in Phase 2.
- **`__tt`** is built by `createTT(host)` (accessors over `App`), after `RAPIER.init()`; before that
  `window.__tt` is a `bootTT()` stub with `state: 'boot'`. `state` is read-only through `__tt`.
  `app.rendererString` is kept from Phase 0 (the smoke test uses it instead of
  `app.renderer.getContext()`). `fastForward` returns early when `until` is reached or the level is
  finished; when `until` equals the current state it returns `{ state, seconds: 0 }`.
- **`tuning.smoke` (the Phase 0 demo scene constants) is deleted** with the demo scene; new blocks
  `physics`, `camera`, `render`, `ballVisual`, `autopilot` and the collider materials under `track`
  hold every new number. The one remaining literal is the catch plane's 0.5 m thickness (geometry,
  not a tunable).
- **Boot goes straight into `levelTest`** (default tier Tiny) and `state` goes `boot -> playing`. The
  Phase 0 smoke test now waits for `playing` instead of `title` and asserts the ball makes progress
  along the track instead of coming to rest on a plane (the plane no longer exists); everything else
  in it is unchanged.

## 31 Oct 2026 — Phase 2 decisions

**Review fixes (Phase 1b code review)**

- **`fastForward` lives in `src/app/fastForward.ts`** (`fastForwardSim`) so it can be unit tested without
  a renderer; `App.fastForward` is a thin wrapper. It calls `Input.update(1 / physicsHz)` per step, so
  the 500 ms lockout expires and the keyboard ramps during a fast-forward.
- **`Input.update` only counts the part of a frame after the lockout ended** toward the keyboard ramp,
  and the ramp target is 0 while locked, so a key held through a state change eases in from 0 instead of
  jumping to full steer. `release()` and `lock()` keep key state; a new `clearKeys()` is called on
  `blur` and `hidden` only (key-up events may never arrive then). `App.resize` no longer touches the
  viewport or releases the pointer (`Input.attach` owns both).
- **Dead zone** is `sign(dx) * clamp((|dx| - dz) / (range - dz), 0, 1)`; it returns exactly `0` (never
  `-0`) inside the dead zone. The old test that asserted steer 0.5 at half range was updated to the new
  formula (the behaviour change is the point of the fix).
- **Parking brake**: `brakeDamping` is now also the angular damping while not driving. Measured: the ball
  still creeps down a 15 degree ramp at about 0.74 m/s (was about 1 m/s). Linear damping is a drag
  proportional to speed, so the terminal creep speed is gravity along the slope (rolling: 5/7 g sin 15 =
  1.81 m/s^2) over the damping, 0.72 m/s. Damping can never fully hold a ball on a slope; see PROGRESS.
- Existing tests touched, not weakened: the steer-parks-a-lane test runs on `levelTest` without
  obstacles (a Big kid ball held at full right steer now correctly drives into the pillar at +0.9);
  the "accepts the boundary lengths" rule-1 test uses a fixture that also satisfies rules 2-7.

**Track system**

- **New files** (PLAN section 4 lists none of these): `MeshBuilder.ts` (the triangle-soup builder that
  was private to `Track.ts`, plus oriented boxes and baking of three primitives), `Arches.ts`
  (checkpoint and finish arches, flag cloth), `LevelView.ts` (everything visible except the ball, built
  from a `GameWorld`; unit testable in Node because it needs no GL context), `Contacts.ts` (the
  contact-event filter). `App` now only owns the renderer, camera, input and state machine.
- **`validateLevel`**: rule 1 is a precondition (if the points are unusable, only rule 1 errors are
  returned, which is what the Phase 1a tests expect). Rules 3 and the slope-window checks are done on
  the frames. Turning radius is the _plan-view_ (XZ) radius from the heading change between the
  neighbouring frames; vertical curvature is ignored (walls are vertical and the ball steers in plan).
  Self-intersection: frames more than `3.2 x width` apart along the arc must be at least
  `width + 2 x 0.3` apart in plan view (with radius >= width, nearer parts are adjacent by construction).
  Pillar/gate slope is checked on frames within 1 m of `atM`, the bend radius within 4 m. Two small
  extras under rule 5 that are physically necessary and not in the plan's list: a bump must fit inside
  the track (`|offset| + width/6 <= width/2`) and a balloon must be at least 0.5 m from the wall. The
  offset limits compare with a 1e-9 tolerance so a value exactly on a limit passes.
- **Walls**: `TierTuning.wallMode` (tiny `full`, bigkid `low`) holds the defaults; the level overrides
  per tier. `noWallSpansM` is passed for Big kid only.
- **`buildColliders`**: the wall collider is `null` when the wall geometry has no triangle. The floor
  collider throws a clear error instead (a track with fewer than 2 frames is a programming error).
- **Start pad**: the _half_ of the 3 m disc behind frame 0 is added to the floor geometry as a flat fan in
  frame 0's plane (the front half coincides with the track floor; building it would z-fight). Palette
  `accent` colour. The ball spawns at frame 0 (`startArcM` is now 0).
- **Pillar**: `roundCylinder` with the 0.05 m border inside the 0.4 m radius / 2.0 m height, so the
  rounded shape is exactly r 0.4, h 2.0 (verified by ray casts). The 0.3 m conical skirt also gets a cone
  collider (kind `pillar` / `gate`), otherwise the ball would roll visibly through the flange; PLAN
  lists only the `roundCylinder`.
- **Bump**: height is `sin^2` along the track (zero slope at both ends, 0.2 m peak) and eases down over
  0.25 m at the lateral ends; the base sits 3 cm below the floor so there is no visible seam. Visual and
  collider are the same vertices; one trimesh for all bumps in a level.
- **Gate**: the banner floats at 6 m with two thin visual strings down to the post tops (no collider
  anywhere above 2 m). The camera sits about 4.5 m above the floor, so a banner at 6-6.9 m is only a
  risk when the track climbs steeply within 7 m after a gate (PROGRESS, "look at next").
- **Balloon**: the sphere centre (not the bottom) is 1.2 m above the floor, along the frame's `up`, so
  a ball on the floor (centre 0.5 m up) pops it from 0.85 m to either side. Popped balloons stay popped
  for the rest of the level (also after a respawn). Popping is a distance check at the end of
  `GameWorld.step`; the pop animation (scale burst) is visual and driven by the render loop.
- **Arches**: posts stand 0.5 m outside the outer face of the walls; the beam's underside is 7.5 m above
  the floor (the camera is about 4.5 m up, so it passes under; the plan's "no lintels" cannot mean
  arches, only the gate banner and colliders). Checkpoint flags: a pole on the beam and a swallowtail
  cloth (one `InstancedMesh`) that slides down 0.7 m and spins two turns when the checkpoint is passed;
  the shape and pose change, the colour never does. The view reads `progress.checkpointsPassed`
  (updated by the Progress checkpoint event); a view created after a checkpoint shows it already
  dropped. `prefers-reduced-motion` drops without spinning. The finish arch is chequered (pattern).
- **Decor**: rejection sampling against the plan-view distance to the nearest centreline frame (8-16 m,
  inset 5 cm because nearest-frame distance over-estimates the distance to the polyline), so decor is
  never closer than 8 m even where the track curves back. Trees and discs sit 0.3 m below their frame's
  floor, clouds float 4-9 m above it; there is no ground plane (the fog and sky hide the void). Cloud
  vertex colours are multiplied by `tuning.decor.cloudBrightness` (1.45) so Lambert shading clamps to a
  soft white instead of grey.
- **Contact events**: `ActiveEvents.CONTACT_FORCE_EVENTS` on the ball collider with a force threshold of
  `impulseThreshold (0.5 N s) x physicsHz`. A force event is "new" when that collider had none in the
  previous 6 steps; floor / catch-plane events are dropped; 1 s refractory per collider handle and at
  most 2 per rolling second overall; everything counts physics steps (no clock). `GameWorld` also
  emits `pop` and `checkpoint` events (Phase 5 will want them); `drainEvents()` hands them over and
  `App` currently drops them. Note all wall segments are one trimesh collider, so the per-collider
  refractory is per wall mesh, not per segment.
- **Autopilot repulsion** (PLAN section 13) looks at the _nearest group_ of posts (a gate's two posts
  count together) from 1 m behind to 6 m ahead, not at every post in the window: with pillars alternating
  sides 3 m apart, the two overlapping windows pushed in opposite directions and the ball hit the first.
- **`__tt`** gained `balloons()` and `obstacles()` (read-only counts) so e2e can assert on them.
- **`levelTest`** keeps its geometry and checkpoints (25 / 50 / 72). Obstacles: bumps 12 / 34, balloons
  19 / 41 / 62 / 84 (offsets 0, 0.4, -0.4, 0 so the autopilot's centreline pops them all), Big kid only:
  pillars at 8 m (+0.9) and 68.5 m (-0.9), a gate at 46 m. They sit on the only places that satisfy the
  validator: flat, straight, away from the S-bend (radius under 12 m up to about 42 m) and the ramps.
